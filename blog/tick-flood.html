초당 수백 건의 틱, 상태 커밋은 초당 두 번

시세표를 틱이 오는 속도로 다시 그릴 이유는 없다. 배칭으로 커밋 횟수를 고정하고, memo 비교에서 children을 빼고, 503개 행 중 12개만 그리게 했다.

엔지니어링 2026.06.09 읽는 데 7분
이 글의 배경

SEEDTICK 이전 과도기 프로젝트 두 개에서 겪은 일이다. 실시간 스캔 화면의 배칭·memo는 웹(브라우저) 시뮬레이터에서, 종목 선택 리스트의 가상화는 React Native 앱에서 나온 이야기다. 각 사례가 어느 환경인지 본문에 구분해 적었다.

수십 종목을 실시간 구독하면 웹소켓 메시지는 장이 활발할 때 초당 수백 건까지 들어온다. 처음 만든 코드는 정직했다. 메시지 한 건 = 상태 업데이트 한 번. 그리고 화면은 정직하게 죽었다. 스크롤이 끊기고, 틱이 몰리는 순간마다 테이블 전체가 다시 그려졌다.

고치면서 배운 건 하나의 원칙으로 요약된다. 데이터가 오는 속도와 화면을 그리는 속도는 별개의 문제고, 그 사이에 완충 계층이 있어야 한다.

1. 배칭 — 틱은 쌓고, 커밋은 500ms에 한 번 (웹)

사람이 시세표에서 읽을 수 있는 갱신 속도는 초당 두어 번이면 충분하다. 그런데 코드는 초당 수백 번 커밋하고 있었다. 그래서 수신과 커밋을 분리했다. 틱이 오면 상태를 건드리지 않고 티커별 버퍼에 최신값으로 덮어쓰기만 한다(coalescing — 같은 종목의 중간 틱은 화면에 그릴 필요가 없으니 버린다). 커밋은 타이머가 500ms마다 한 번, 버퍼를 통째로 비우면서 한다.

// 수신부: 상태를 건드리지 않는다. 티커별 최신값 덮어쓰기만.
this.updateBatch[ticker] = {
  price: parseFloat(fields[11]),
  change: parseFloat(fields[13]),
  rate: parseFloat(fields[14]),
  volume: parseFloat(fields[19]),
};

// 커밋부: 500ms마다 한 번, 모아서 단일 상태 업데이트
startFlushTimer() {
  this.flushTimer = setInterval(() => {
    if (Object.keys(this.updateBatch).length > 0) {
      const batch = this.updateBatch;
      this.updateBatch = {};
      useStore.getState().batchUpdateRealtimePrices(batch);
    }
  }, 500);
}

효과는 구조적으로 보장된다. 틱이 초당 10건이든 500건이든, React가 겪는 상태 커밋은 초당 최대 2회로 고정된다. 부하의 상한을 데이터가 아니라 코드가 정하게 된 것이다.

작은 트레이드오프도 하나 있었다. stopFlushTimer()에서 버퍼를 같이 비웠더니, 타이머를 잠깐 멈췄다 재개하는 경로에서 마지막 배치가 유실됐다. 그래서 타이머 정지와 버퍼 초기화의 책임을 분리했다 — 정지는 타이머만 멈추고, 버퍼를 비우는 건 연결을 완전히 닫는 쪽(disconnect)의 일로 넘겼다. "정리(cleanup)"라는 단어 아래 서로 다른 두 작업이 숨어 있었던 셈이다.

2. memo가 안 듣던 이유 — children은 매번 새 객체다 (웹)

배칭으로 커밋을 줄여도, 커밋 한 번에 테이블 전 행이 다시 그려지면 소용이 없다. 행 컴포넌트를 memo로 감쌌는데 효과가 없었다. 원인은 children이었다. 부모가 렌더링될 때마다 children으로 내려오는 JSX는 항상 새 객체라서, 기본 얕은 비교로는 매번 "props가 바뀌었다"로 판정된다. memo가 무력화되는 것이다.

그래서 비교 함수를 직접 쓰고, children을 비교에서 의도적으로 제외했다. 행의 실제 데이터 필드만 본다.

export const AnimatedTableRow = memo(AnimatedTableRowComponent, (prevProps, nextProps) => {
  // children은 매번 새로운 객체이므로 비교에서 제외하고,
  // 실제 데이터(item)가 변경되었을 때만 리렌더링하도록 함.
  const prev = prevProps.item, next = nextProps.item;
  return (
    prev.ticker === next.ticker &&
    prev.price === next.price &&
    prev.changeRate === next.changeRate &&
    prev.signal === next.signal &&
    prev.sentiment === next.sentiment &&
    prev.reason === next.reason
  );
});

이 방식은 "children이 item에서만 파생된다"는 전제를 깔고 있어서, 그 전제가 깨지면 화면이 낡은 값을 보여주는 버그가 된다. 전제를 주석으로 박아 두는 것까지가 최적화의 일부다.

3. 가상화 — 503개 행을 12개부터 그리기 (RN)

React Native 앱 쪽에서는 다른 형태로 같은 문제를 만났다. S&P500 종목(503개)을 고르는 바텀시트를 ScrollView + map()으로 만들었더니, 여는 순간 503개 행이 전부 한 번에 마운트됐다. 각 행에는 원격 SVG 로고를 불러오는 컴포넌트까지 붙어 있었다. 시트가 열릴 때마다 프레임이 떨어지고, 검색어를 한 글자 칠 때마다 전체 행이 다시 계산됐다.

FlatList로 바꾸고 가상화 파라미터를 조였다.

<FlatList
  data={filteredStocks}
  keyExtractor={(item) => item.stock}
  renderItem={renderStockItem}      // useCallback으로 참조 고정
  initialNumToRender={12}           // 첫 화면에 보이는 만큼만
  maxToRenderPerBatch={10}
  windowSize={5}
  removeClippedSubviews={true}
/>

수치의 근거는 화면이다. 바텀시트에 한 번에 보이는 행이 10~12개라 initialNumToRender=12면 첫 프레임에 필요한 만큼만 그린다. windowSize=5는 보이는 영역의 위아래 2화면분만 유지한다는 뜻이다. 여기에 renderItem을 useCallback으로 고정하고 행과 로고 컴포넌트를 React.memo로 감쌌다 — 가상화는 "몇 개를 그리느냐"를 줄이고, memo는 "그린 것을 다시 그리느냐"를 줄인다. 둘은 대체재가 아니라 곱해지는 관계다.

4. 덤 — 강조 표시가 리스트를 들썩이게 한 이유 (RN)

가격 급변 종목을 강조하려고 행에 빨간 테두리를 붙였더니 리스트 전체가 들썩였다. 테두리 두께만큼 행 높이가 바뀌어 레이아웃 재계산이 일어난 것이다. 강조를 테두리 대신 backgroundColor 페이드 애니메이션으로 바꿨다 — 배경색은 레이아웃에 영향을 주지 않는 속성이라 행 높이가 고정된다. "무엇을 애니메이션하느냐"가 "애니메이션을 하느냐"보다 성능에 더 크게 작용했다.

정리, 그리고 반성

  • 수신 속도와 렌더 속도를 분리한다. 완충 버퍼 + 고정 주기 커밋으로 부하 상한을 코드가 정하게 한다.
  • memo는 걸었다고 끝이 아니다. 무엇이 비교되는지 확인해야 한다. children은 매번 새 객체다.
  • 그리는 개수를 줄이고(가상화), 다시 그리는 횟수를 줄이고(memo), 레이아웃을 건드리지 않는다(애니메이션 속성 선택).
반성

이 작업들의 아쉬운 점을 하나 적어 둬야 한다. before/after 프로파일 수치를 남기지 않았다. "틱 N건 → 커밋 초당 2회", "마운트 503행 → 12행"처럼 구조적으로 보장되는 개선은 말할 수 있지만, "프레임 타임이 몇 ms에서 몇 ms가 됐다"는 말할 수 없다. 체감으로는 분명했지만 체감은 근거가 아니다. 그 뒤로는 최적화를 시작하기 전에 계측부터 남기는 걸 규칙으로 삼았다.

이 글은 SEEDTICK 이전에 만든 개인 프로젝트에서 겪은 일을 다룬 엔지니어링 기록이에요. 투자 권유가 아니며, 매매 결과에 대한 책임은 사용자에게 있어요.
